  9. VULNERABILIDADE CORRIGIDA — /api/coordenadas vazava o carteira
     de qualquer coordenada pública. Achado durante conversa com o
     Renner sobre segurança por coordenada/distância no espaço 3D.
     GRAVIDADE: crítica — carteira é o único "segredo" que os
     endpoints de edição (PATCH /api/url, /api/url3d, /api/nome,
     /api/privacidade) conferem, sem assinatura nem sessão. Qualquer
     visitante conseguia listar coordenadas públicas via essa rota,
     pegar o carteira de qualquer uma, e sequestrar/deface o conteúdo
     dela. Fix: removido carteira do SELECT de /api/coordenadas —
     cliente nunca usava esse campo (carregarCoordenadas só lê
     coord_x/y/z e url_3d). Conferidos os outros SELECT * do
     server.js — todos exigem que o próprio carteira seja fornecido
     como entrada (não vazam o de terceiros).

     PROBLEMA DE FUNDO AINDA ABERTO (não é sobre esse vazamento
     específico, é maior): o carteira nunca teve verificação
     criptográfica de verdade — é só uma string (UUID gerado no
     dispositivo) que "quem souber, usa". Isso significa:
       → Sem assinatura de carteira Solana nem sessão, qualquer
         vazamento futuro do carteira (novo endpoint mal feito, log,
         etc.) repete esse mesmo problema.
       → Fluxo de "reconhecimento" (mostrarReconhecimento/
         confirmarReconhecimento) deixa qualquer um clicar "SIM, é
         minha" em qualquer coordenada registrada sem nenhuma
         verificação — não dá poder de edição de verdade (o servidor
         ainda exige o carteira certo), mas é uma UX enganosa.
       → Se o usuário perder o dispositivo/limpar localStorage, não
         tem como recuperar o carteira original — ele sabe a
         coordenada (a "senha" documentada) mas não consegue mais
         editar nada.
     SUGESTÃO PARA O FUTURO (não implementado, não pedido ainda):
     autenticação real via assinatura de carteira Solana resolveria
     os três pontos de uma vez — fecha vazamento por definição e
     dá recuperação de conta em novo aparelho.

  10. AUTENTICAÇÃO TOTP — implementada (resolve o ponto 9 acima)
      Decisão do Renner: TOTP padrão (RFC 6238, o mesmo do Google
      Authenticator/Authy/qualquer app compatível) obrigatório em
      TODA coordenada — sem códigos de backup, sem sync com conta
      Google. Filosofia explícita: "perdeu a chave, perdeu a
      coordenada" — mesma lógica de self-custody de carteira cripto
      (Bitcoin/Solana), coerente com o resto do produto.

      O carteira deixou de ser a trava (Opção A discutida) — agora
      ele só identifica a linha no banco. Quem decide se pode editar
      é uma sessão temporária (JWT, 30min) emitida só depois de um
      código TOTP válido.

      NOVO NO BANCO (registros):
        totp_secret     TEXT    — chave TOTP (null até configurar)
        totp_confirmado BOOLEAN — true só depois do primeiro código
                                   confirmado com sucesso

      NOVOS ENDPOINTS (server.js):
        POST /api/totp/iniciar        { carteira } → gera/reaproveita
             a chave e devolve QR code (preto sobre branco — precisa
             ser lido por app de terceiros, diferente do QR do Solana
             Pay que é branco sobre transparente)
        POST /api/totp/confirmar      { carteira, codigo } → confirma
             o primeiro código, ativa totp_confirmado, devolve sessão
        POST /api/totp/login          { carteira, codigo } → login de
             quem já tem TOTP configurado, devolve sessão
        GET  /api/totp/status/:carteira → { configurado: bool }, usado
             pelo cliente pra decidir entre tela de SETUP ou LOGIN

      ENDPOINTS PROTEGIDOS (agora exigem totp_confirmado=true no banco
      E header Authorization: Bearer <sessão válida>):
        PATCH /api/url, /api/url3d, /api/privacidade, /api/nome

      MIGRAÇÃO: coordenadas registradas antes desta feature existir
      não têm totp_secret ainda. Na primeira vez que tentarem editar
      algo, garantirSessao() no cliente detecta totp_confirmado=false
      via /api/totp/status e abre o setup automaticamente — não existe
      caminho pra editar sem passar por isso, nenhuma coordenada fica
      de fora.

      NOVO NO CLIENTE (index.html):
        #modal-totp — um modal só, dois estados visuais (setup mostra
        QR + chave manual; login só pede o código)
        garantirSessao(aoConcluir) — função central: se já tem sessão
        válida no localStorage (cosm_sessao), roda aoConcluir() na
        hora; senão abre o modal certo e só roda aoConcluir() depois
        do código confirmado
        Fluxo de registro (confirmarBetaRegistro): depois do
        POST /api/beta/claim, chama garantirSessao() ANTES de mostrar
        a tela final "ANOTE AGORA" — TOTP é obrigatório desde o
        primeiro registro, não dá pra pular
        salvarUrlNoEspaco() virou o único caminho pra persistir
        conteúdo (PATCH /api/url e /api/url3d) — agora sempre passa
        por garantirSessao() e manda o header Authorization

      BUG PRÉ-EXISTENTE CORRIGIDO DE PASSAGEM: testarInserir() nunca
      chamava salvarUrlNoEspaco() no caminho de conteúdo web/iframe —
      só no caminho de objeto 3D (.glb). O banner dizia "✓ SALVO NO
      SEU ESPAÇO" mas url_conteudo nunca era persistido de verdade.
      Corrigido porque tocava direto na mesma função que ganhou o
      gate de TOTP — sem isso, o gate nem faria diferença nesse
      caminho (mais comum que o de .glb).

      DEPENDÊNCIAS NOVAS (package.json): otplib, jsonwebtoken.

  12. BUG CORRIGIDO — /api/beta sempre mostrava todas as vagas livres
      Causa: coord_x/y/z voltam do Postgres como STRING (coluna
      BIGINT), mas eram comparados com === contra os números literais
      de BETA_COORDS — "0" === 0 é sempre falso em JS. Resultado:
      ocupado nunca batia, então o grid de escolha de vaga no
      REGISTRAR sempre mostrava as 10 como "LIVRE", mesmo quando já
      tomadas. A checagem de "já ocupado" dentro do claim (SQL direto,
      não JS) sempre esteve correta — só a listagem pra exibir estava
      errada. Fix: Number(r.coord_x) === c.x nos três eixos.
      Achado ao investigar um pedido do Renner pra identificar quais
      vagas eram dele — testado isoladamente com dado simulado do
      Postgres antes do push, confirmado ao vivo depois do deploy
      (vaga 10 passou a aparecer ocupada corretamente).

        fica fora do alcance. Confirmado ao vivo: os 4 arquivos
        internos agora dão 404, as páginas públicas continuam 200.
        Também: novo .gitignore (node_modules nunca vai pro repo,
        risco real depois que instalei Node localmente nesta sessão)
        e package-lock.json commitado.

      15b. CRÍTICO — totp_secret vazando em texto plano
        Todo SELECT * ou RETURNING * na tabela registros devolvia
        também a coluna totp_secret pra quem recebesse a linha —
        em GET /api/coordenada/:carteira, POST /api/registrar (as
        duas branches), POST /api/beta/claim, e as 3 variações
        dentro do fluxo de pagamento Solana. Combinado com QUALQUER
        vazamento futuro do carteira de alguém (mesma categoria do
        vazamento em /api/coordenadas corrigido antes nesta sessão),
        isso permitiria gerar códigos TOTP válidos pra sempre —
        sequestro de conta permanente, apesar de toda a arquitetura
        de sessão que construímos.
        Fix: const REGISTRO_COLS com lista explícita de colunas
        seguras (todas menos totp_secret), usada em toda query que
        devolve a linha ao cliente. Os endpoints de TOTP em si
        continuam usando SELECT totp_secret, totp_confirmado
        explicitamente (já eram mínimos, não precisaram mudar).
        Confirmado ao vivo: totp_secret sumiu de todas as respostas,
        totp_confirmado (seguro, é só boolean) continua aparecendo.

      15c. GAP FUNCIONAL — visitante não via conteúdo tipo "página web"
        Achado testando exatamente o cenário que o Renner descreveu:
        "digitar a coordenada de alguém e ver o que ele registrou,
        como se estivesse no PC da pessoa mas no espaço."
        carregarCoordenadas() carrega objetos 3D (.glb) de TODAS as
        coordenadas públicas na cena ao carregar a página — mas não
        existia nenhum código que mostrasse url_conteudo (site) pra
        um visitante. abrirIframeNoEspaco() só era chamada pelo
        próprio dono, no momento de inserir conteúdo. Resultado:
        alguém visitando a coordenada de outra pessoa com conteúdo
        tipo "página web" via espaço vazio.
        Fix: nova abrirConteudoVisitante(), chamada dentro da
        sequência de chegada do teletransporte (irParaCoordenada())
        quando /api/minha-coord devolve url_conteudo — mostra o
        conteúdo pra QUALQUER visitante. Se não tiver url_conteudo,
        mantém o comportamento antigo (prompt de reconhecimento de
        dispositivo). Verificado com dado real de produção (a URL
        "https://exemplo.com" da minha coordenada de teste) — não
        deu pra clicar visualmente (sem Chrome real disponível nesta
        sessão), mas testei a lógica de prepararUrl() isolada com
        Node e bate exatamente com o que o servidor devolve.

  17. BUG DE ESCALA CORRIGIDO — carregamento de objetos 3D virou sob
      demanda por distância (2026-07-10). Renner perguntou (pensando
      no futuro, com muita gente registrando jogos pesados) se isso
      deixaria o COSM lento. Resposta: o servidor do COSM não seria
      afetado (ele só guarda um texto curto, o arquivo pesado fica
      hospedado fora) — MAS o cliente tinha um bug real: toda vez que
      QUALQUER visitante abria a página, carregarCoordenadas() baixava
      e renderizava o .glb de TODAS as coordenadas públicas de uma vez,
      não importa a distância. Com poucos registros isso é invisível;
      com milhares, o navegador de CADA visitante tentaria baixar o
      universo inteiro assim que abrisse a página.
      Fix: nova registrarObjeto3DDistante() — só guarda a coordenada,
      NÃO baixa nada. atualizarObjetos3D() (já rodava todo frame) agora
      também varre essa lista e só chama carregarObjeto3D() quando o
      visitante entra no raio OBJ_LOAD_DIST (3000u) — carregamento por
      distância, igual jogo de mundo aberto. OBJ_DIST_MAX (500u,
      visibilidade) continua existindo numa camada separada, só pra
      decidir o que fica visível dos objetos JÁ carregados.
      Chamadas diretas de carregarObjeto3D() no fluxo de INSERIR (o
      dono adicionando conteúdo na hora, na própria coordenada) não
      mudaram — fazem sentido carregar na hora mesmo.

  18. SECURITY FIX — url_conteudo/url_3d aceitavam qualquer esquema
      (2026-07-10). Achado pensando com o Renner sobre até onde vai a
      responsabilidade do COSM vs. do criador de conteúdo — ele
      perguntou se o hacker atacaria "pela renderização" em vez do
      núcleo do COSM. Resposta: sim, e havia um vetor real pra isso —
      PATCH /api/url, PATCH /api/url3d e POST /api/beta/claim gravavam
      a URL exatamente como recebida, sem checar o esquema. Esse valor
      vira o src de um <iframe> (visitante) ou a URL passada ao
      GLTFLoader — sem validação, uma coordenada podia registrar
      "javascript:..." no lugar de um site normal, atacando quem
      visitasse, não o próprio dono.
      Fix: nova validarUrl() — exige https:// no começo, rejeita
      javascript:, data:, http:// comum e qualquer outro esquema.
      Aplicada nos 3 endpoints que aceitam url/url_3d do cliente.
      Testado ao vivo: javascript:alert(1) rejeitado com 400 antes
      até de chegar na checagem de sessão TOTP; https:// normal
      continua funcionando e persistindo certinho.
      PRINCÍPIO GERAL que ficou definido nessa conversa (vale lembrar
      em decisões futuras): conteúdo hospedado externamente pelo
      criador (o site/jogo em si) é responsabilidade DELE — o COSM não
      tem visibilidade sobre isso. Mas COMO o COSM pega esse conteúdo
      e encaixa na tela (validação de esquema, sandboxing de iframe,
      etc.) é responsabilidade do COSM.

  19. CÓDIGO AO VIVO — persistência NÃO implementada, risco identificado
      (2026-07-10, decisão pendente). Renner confirmou que o "código
      ao vivo" (Tipo 3, Three.js) precisa passar a persistir de verdade
      — hoje ele só aparece na sessão de quem escreveu e some ao
      recarregar, nunca fica visível pra outros visitantes (diferente
      de objeto 3D e página web, que persistem normalmente).
      NÃO IMPLEMENTADO DE PROPÓSITO: salvar o código e reexecutá-lo
      automaticamente pro navegador de QUALQUER visitante que chegar
      na coordenada seria uma vulnerabilidade grave — o código rodaria
      com os mesmos privilégios da própria página do COSM no navegador
      do visitante, podendo ler localStorage (cosm_id, cosm_sessao) e
      agir em nome dele. Hoje isso não é risco porque o código só roda
      na sessão de quem escreveu (não pode prejudicar só a si mesmo).
      O jeito certo de resolver: isolar a execução (ex: rodar dentro
      de um iframe sandboxed próprio, não na página principal) antes
      de persistir — trabalho real, não ajuste rápido. Aguardando
      decisão do Renner: desenhar essa versão seguro, ou deixar
      "código ao vivo" como está (demonstração temporária) por
      enquanto.

a engine verifica se existe window._cosmLoop e/ou window._cosmControls.

  window._cosmLoop = (dt) => {
    // dt = delta time em segundos
    // chamado todo frame dentro de loop() do COSM
    // enquanto visitante estiver na área da coordenada
    meuObjeto.rotation.y += dt * 0.5
    meuObjeto.position.y = Math.sin(Date.now() / 600) * 20
  }

  window._cosmControls = false
  // false = desativa mouse/teclado padrão do COSM
  // dev controla câmera livremente
  camera.position.set(0, 80, 200)
  camera.lookAt(0, 0, 0)

Ao sair da área: _cosmLoop e _cosmControls são removidos (= undefined).
Área definida por distância da coordenada registrada (OBJ_DIST_MAX).

ESCALA DO HUD — formatCoord + zonaAtual

  function formatCoord(v) {
    const s = v < 0 ? '-' : '';
    const a = Math.abs(v);
    if (a >= 1e9) return s + (a/1e9).toFixed(2) + 'A'; // Anos-luz
    if (a >= 1e6) return s + (a/1e6).toFixed(2) + 'S'; // Setor
    if (a >= 1e3) return s + (a/1e3).toFixed(1) + 'k'; // Pessoal
    return s + Math.round(a) + 'm';                      // Local
  }

    if (m >= 1e3) return { label:'PESSOAL',  cor:'rgba(100,255,180,0.7)' };
    return             { label:'LOCAL',     cor:'rgba(255,255,255,0.4)' };
  }

ALOCAÇÃO DE COORDENADAS — server.js
  Pessoas: Esfera de Fibonacci → distribui em X, Y, Z (não espiral 2D)
  Empresas: Eixo X exclusivo (bloco de 1M por empresa)
  GAP = 1.000.000 → espaço enorme, coordenadas embaralhadas (intencional)
  O embaralhamento vem da fórmula Fibonacci, não de aleatoriedade.

  const GAP = 1_000_000;

  function alocarCoordenada(totalPessoas) {
    const i     = totalPessoas;
    const phi   = Math.acos(1 - 2 * (i + 0.5) / 10000);
    const theta = i * 2.39996322972; // ângulo áureo em radianos
    const r     = GAP * Math.sqrt(i + 1);
    return {
      x: Math.round(r * Math.sin(phi) * Math.cos(theta)),
      y: Math.round(r * Math.cos(phi)),
      z: Math.round(r * Math.sin(phi) * Math.sin(theta))
    };
  }

  function alocarCoordenadaEmpresa(n) {
    return { x: (n + 1) * 1_000_000, y: 0, z: 0 };
  }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

VISAO:
  Drive pessoal dentro do universo. Arquivos guardados na coordenada.
  Visibilidade por arquivo: PUBLICO (aparece pra quem visita) ou
  PRIVADO (so o dono acessa via link direto sem rastro de quem e).

STORAGE:
  Opcao escolhida (ainda nao implementado): IPFS via Pinata
  Mais nos na rede = mais rapido (igual BitTorrent)
  Filosofia alinhada com COSM: decentralizado, sem dono central
  Alternativa simples por enquanto: usuario cola URL de qualquer hospedagem

LAYOUT DEFINIDO — 3 abas no painel MEU ESPACO:
  1. ARQUIVOS: lista/grade com upload, toggle publico/privado, ver, baixar, copiar link, apagar
  2. COMPARTILHAR: coord inteira (mostra publicos) ou link direto por arquivo
  3. VISIVEL NA COORD: previa do que visitante ve

BANCO — tabela nova necessaria:
  arquivos (id, uuid_dono, nome, url_ipfs, tipo, tamanho_bytes, publico BOOLEAN, criado_em)
  Multiplos arquivos por coordenada (diferente de url_conteudo que e 1 por coord)

PARA IMPLEMENTAR:
  1. Conta Pinata (gratis) + API Key
  2. Endpoint /api/upload no server.js (multer + Pinata SDK)
  3. Endpoint /api/arquivos/:uuid (lista arquivos do dono)
  4. Endpoint /api/arquivo/:id/visibilidade (toggle publico/privado)
  5. Painel COSM Drive no index.html (design definido em mockup)

  JOGOS NO COSM — CONCEITO DEFINIDO (2026-07-04)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

VISAO:
  A coordenada E o endereco do jogo. Nao tem launcher, nao tem download.
  Voce voa ate COSM://5000000:0:0 e entra no jogo. Igual o cassino-planeta
  do filme — voce simplesmente chega la.

3 NIVEIS DE JOGO:
  Nivel 1 — Jogo simples (card CODIGO):
    Escreve Three.js com interatividade. Roda direto na engine do COSM.
    Fisica, colisao, eventos de teclado — tudo possivel hoje.
    Single-player, sem servidor extra.

  Nivel 2 — Jogo medio (url_conteudo):
    Developer faz um jogo web completo (Unity WebGL, Phaser, Babylon.js, etc.)
    Hospeda em qualquer lugar e aponta a URL para a coordenada.
    Quem voa ate la entra no jogo via iframe. Sem launcher, sem instalacao.

  Nivel 3 — Jogo pesado/multiplayer:
    Developer roda servidor proprio (WebSocket, game server).
    COSM aponta a coordenada para esse servidor.
    Jogadores que chegam conectam ao servidor do jogo.
    Developer paga pelo servidor conforme necessidade de performance.
    O COSM nao hospeda — so enderea.

MONETIZACAO (A IMPLEMENTAR):
  → Acesso pago a coordenada: developer vende ingresso (token/chave)
    para entrar no jogo. Quem nao tem o token nao acessa o conteudo.
  → Venda de jogabilidade: itens, fases, power-ups dentro do jogo
    (depende do sistema do proprio jogo — COSM nao controla)
  → Royalty COSM: % nas transacoes feitas dentro do universo (marketplace)
  → Performance tier: developer paga por CDN premium para servir
    assets pesados mais rapido (nao via COSM — via servico externo)

REGRAS DO ESPACO:
  Developer pode definir o ambiente 3D ao redor do jogo:
  shader customizado, fisica, objetos decorativos, musica.
  Hoje ja possivel via CODIGO + _cosmAnimHooks.
  Futuro: API de espaco que permite declarar fisica e visual da zona.

O QUE AINDA PRECISA SER CONSTRUIDO:
  → Controle de acesso por coordenada (publico/restrito/pago)
  → Sistema de token/ingresso para entrada em coordenadas pagas
  → Marketplace de jogos (coordenadas com jogo + preco de acesso)
  → Talvez: tipo de conteudo JOGO no modal INSERIR

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FRASE DO FUNDADOR:
  "Estou criando uma plataforma rentavel para qualquer um
   ganhar dinheiro no meu COSM com seguranca e privacidade."

O QUE ISSO SIGNIFICA NA PRATICA:
  → Qualquer pessoa registra uma coordenada (gratis, sem identidade real)
  → Coloca o que quiser nela: jogo, arte, loja, evento, drive, codigo
  → Cobra acesso, cobra por arquivo, cobra por fila, cobra por experiencia
  → Recebe pagamento via Solana (sem banco, sem CPF, sem rastreamento)
  → O COSM processa e retem 10% automaticamente — o resto vai pro criador
  → O visitante nao sabe quem e o dono — so sabe a coordenada
  → O dono nao sabe quem e o visitante — so sabe o UUID anonimo

TRES PILARES:
  1. RENTAVEL — qualquer coordenada pode virar negocio
     Jogo, museu, show, loja, escola, cassino, campo, leilao
     Developer define preco, regras, acesso — COSM so cobra 10%

  2. SEGURO — infraestrutura que nao expoe ninguem
     Usuario = UUID (sem nome, sem email, sem IP registrado)
     Pagamento = Solana (blockchain, sem intermediario bancario)
     Arquivo = IPFS (sem servidor central, sem rastro de origem)
     Coordenada = identidade anonima permanente

  3. PRIVACIDADE — o anonimato e a regra, nao a excecao
     Dono da coord: identificado so pelo UUID no banco interno
     Visitante: identificado so pelo UUID — nao vinculado a pessoa real
     Arquivo privado: link direto sem metadado de quem enviou
     Transacao: blockchain publica mas sem nome vinculado

COMO O COSM GANHA DINHEIRO (modelo definitivo):
  → 10% de toda transacao que passar pela infraestrutura de pagamento
  → Isso acontece automaticamente em toda coordenada comercial
  → Nao precisa monitorar, nao precisa cobrar — a plataforma coleta
  → Escala com o numero de criadores ativos no universo
  → Quanto mais o ecossistema cresce, mais o COSM ganha

ANALOGIAS PARA EXPLICAR EXTERNAMENTE:
  → "E o App Store mas no universo 3D — qualquer coordenada e um app"
  → "E o Shopify mas o endereco da loja fica no espaco"
  → "E o YouTube mas o canal e uma coordenada que voce visita fisicamente"
  → "E o DNS da internet, mas para um universo 3D navegavel"

ORDEM DE CONSTRUCAO (prioridade definida pelo fundador):
  1. Controle de acesso pago por coordenada (ingresso/token)
  2. Marketplace com royalty automatico de 10%
  3. COSM Drive (storage IPFS publico/privado por arquivo)
  4. Visao: relay multiplayer, CDN premium, analytics por coordenada

PROBLEMA CENTRAL DO LANCAMENTO:
  Universo vazio = sem motivo para explorar.
  Sem criadores nao tem visitantes.
  Sem visitantes nao tem criadores.
  A iniciacao precisa resolver isso antes de abrir para todos.

USUARIOS PRIMARIOS — em ordem de prioridade:

  1. DESENVOLVEDORES E CRIADORES 3D (colonizadores)
     Sao os que constroem o conteudo que outros vem ver.
     Um developer que cria um jogo ja traz os amigos.
     Um artista 3D que coloca uma escultura GLB ja compartilha a coord.
     Sem eles o mapa fica em branco.

  2. COMUNIDADE WEB3 / CRIPTO
     Ja pensam em "possuir" espaco digital.
     Privacidade por padrao e exatamente o que querem.
     Solana Pay ja e familiar.
     Coordenada permanente ressoa como NFT mas mais tangivel —
     voce nao compra uma imagem, voce compra um lugar no universo.

  3. DESENVOLVEDORES INDIE DE JOGOS
     App Store cobra 30%, tem aprovacao, tem regras.
     No COSM: registra coord, aponta para o jogo, vende acesso, paga 10%.
     Sem gatekeeper. Muito atrativo para devs independentes.

ESTRATEGIA DE INICIACAO:
  Nao lanca para todo mundo.
  Lanca para 20 criadores escolhidos com coordenadas gratuitas permanentes
  em troca de construir algo impressionante.

  20 coordenadas com conteudo real
      → cada criador compartilha com sua comunidade
      → pessoas voam, ficam impressionadas
      → querem a propria coordenada
      → loop comeca

O MOMENTO QUE CONVERTE:
  O primeiro visitante que chega numa coordenada com jogo funcionando,
  galeria 3D ou experiencia interativa — e percebe que chegou voando
  pelo espaco sem instalar nada — esse e o momento que converte.

PRE-REQUISITO ANTES DE LANCAR:
  Pelo menos 5 coordenadas com algo genuinamente impressionante.
  A tecnologia ja impressiona sozinha, mas precisa de conteudo
  para mostrar o que e possivel. O resto o boca a boca faz.

  COSM CHAT — CONCEITO DEFINIDO (2026-07-04)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

VISAO:
  Chat entre coordenadas. Sem numero de telefone, sem email,
  sem nome. Voce e sua coordenada. Ninguem sabe quem e esse numero.

POR QUE E O MAIS SEGURO:
  WhatsApp/Signal/Telegram: precisam de numero de telefone.
  Isso vincula identidade real. O servidor sabe quem fala com quem.
  COSM Chat: voce e COSM://X:Y:Z. Nada mais.

MODELO DE SEGURANCA — 4 camadas:
  1. Sem identidade real — coordenada anonima, sem vinculo com pessoa
  2. Sem descoberta — para te achar precisa da sua coordenada
  3. Autorizacao obrigatoria — mesmo com a coord, entra so se voce aprovar
  4. Criptografia client-side — servidor guarda so texto cifrado, nao le nada

FLUXO DE AUTORIZACAO:
  Coord A quer falar com Coord B
      → B recebe pedido de autorizacao
      → B aprova: chat abre
      → B ignora: Coord A nao existe para B

DEAD DROP DIGITAL — conceito central:
  No mundo real espiao deixa mensagem num local fisico combinado.
  O outro passa la quando puder, pega, deixa resposta.
  Ninguem viu ninguem. Sem rastro de comunicacao direta.
  No COSM e igual — mensagem fica na coordenada esperando.

DOIS MODOS NATURAIS:
  Modo async (principal):
    Mensagem enviada → fica guardada no servidor cifrada
    Destinatario esta offline → nao sabe de nada
    Destinatario entra na coordenada → mensagem aparece
    Sem notificacao, sem push, sem recibo de leitura
    Sem urgencia, sem pressao, sem rastro de horario de atividade

  Modo ao vivo (automatico):
    Duas coordenadas abertas ao mesmo tempo → vira tempo real
    Um PC fecha → volta para async automaticamente
    Sistema detecta sozinho, sem configuracao

POR QUE NAO TEM PUSH NOTIFICATION (e isso e uma vantagem):
  Push precisa de telefone ou email para chegar.
  Isso vincula identidade.
  No COSM nao tem identidade para notificar.
  O silencio e o sigilo.
  So sabe que tem mensagem quando entra na propria coordenada.

PUBLICO IDEAL:
  → Conversas sem pressa e sem urgencia
  → Pessoas que valorizam privacidade real
  → Jornalistas, ativistas, profissionais sigilosos
  → Qualquer um que nao quer ser rastreado por horario de atividade

TECNICO — O QUE PRECISARIA SER CONSTRUIDO:
  Tabela: mensagens (id, coord_origem, coord_destino, conteudo_encrypted,
          enviado_em, lido_em NULL)
  Tabela: autorizacoes (coord_a, coord_b, status, criado_em)
  Modo async: GET simples ao entrar na coordenada busca mensagens nao lidas
  Modo ao vivo: WebSocket quando ambas coordenadas estao ativas
  Sem WebSocket permanente — so ativa quando as duas estao online juntas
